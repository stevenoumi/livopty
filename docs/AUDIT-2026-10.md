# Audit de reprise : Livopty

Date : 4 octobre 2026
Périmètre : tout le dépôt (`app/`, `components/`, `lib/`, configuration, dépendances).
Vérifications exécutées : `tsc --noEmit` (passe), `pnpm lint` (267 erreurs), `pnpm test` (23 tests, tous verts), `pnpm audit --prod` (51 alertes), compilation Android par Metro (OK).

Limite de l'audit : le projet Supabase (tables, politiques RLS, réglages d'authentification) n'est pas dans le dépôt. Tout ce qui le concerne ci-dessous est donc à vérifier dans le tableau de bord Supabase.

---

## Résumé en dix lignes

1. Livopty est une **app pour couples** ("Simplifiez votre vie à deux") : listes partagées, discussion, budget, agenda.
2. **Seule l'authentification est réelle.** Listes, discussions, budget et profil affichent des données fictives codées en dur dans `lib/data/`. Agenda est un écran vide.
3. La base technique est **moderne et saine** : Expo SDK 57, Expo Router, TypeScript strict, NativeWind, Zod, react-hook-form, i18n. Rien ne justifie une refonte.
4. Il n'y a **aucune déconnexion accessible** et **aucun accès aux paramètres** depuis l'interface.
5. La navigation au démarrage est **décidée à trois endroits différents** qui se contredisent.
6. Le **design system existe sur le papier** (tokens shadcn, `Button`, `Text`, `Input`) mais les écrans ne l'utilisent presque pas : le violet de la marque est codé en dur partout et le token `primary` est... noir.
7. **Sécurité** : pas de faille critique côté app (la clé Supabase embarquée est publique par conception), mais tout repose sur des RLS Supabase non vérifiables ici, le schéma de deep link est incohérent, et il n'y a ni suppression de compte (obligatoire sur l'App Store) ni réinitialisation de mot de passe.
8. **Qualité** : le lint est cassé (configuration incompatible), pas de Prettier, Husky, commitlint ni CI, 2 fichiers de tests seulement.
9. **Release** : `app.json` n'a ni `bundleIdentifier` iOS ni `package` Android, pas d'`eas.json`. L'app ne peut pas encore partir sur les stores.
10. **Verdict** : projet sain à la base, mais c'est un **prototype d'interface avec une authentification branchée**, pas encore un produit. Il faut brancher les données, pas réécrire.

### Les 5 choses à comprendre en premier

1. **Tout est mock sauf l'auth.** Avant toute fonctionnalité, il faut décider du modèle de données Supabase (couple, membres, listes, dépenses, messages).
2. **Le flux de démarrage** (`app/index.tsx` + `AuthContext`) : c'est là que se trouvent les bugs de navigation actuels.
3. **NativeWind et les tokens de `global.css`** : c'est le levier pour rendre le design cohérent rapidement.
4. **`authService.ts` et les schémas Zod** : c'est la partie la plus propre du code, le modèle à suivre pour les futurs services.
5. **La configuration pnpm 11** (`pnpm-workspace.yaml`, `nodeLinker: hoisted`) : NativeWind ne fonctionne pas sans elle.

## 2. Code et architecture

### Ce qui est bien fait (à conserver)

- **`lib/services/supabase/authService.ts`** : un service qui valide, appelle Supabase, traduit les erreurs et renvoie toujours un `AuthResponse` homogène. L'UI ne parle jamais directement à Supabase pour l'inscription et la connexion. C'est le bon patron pour tous les futurs services.
- **`lib/schemas/auth.schema.ts`** : schémas Zod clairs, types dérivés avec `z.infer`, déjà prêts pour "mot de passe oublié" et "réinitialisation".
- **`lib/constants/routes.ts`** : routes centralisées.
- **`AuthContext`** : gestion correcte du démontage (`isMounted`, `unsubscribe`).
- **`supabase.ts`** : `startAutoRefresh` et `stopAutoRefresh` branchés sur `AppState`, comme le recommande Supabase pour le mobile.
- **TypeScript strict qui passe sans erreur** après un an d'inactivité et une montée de version majeure : c'est rare et précieux.

## 3. Design system

### Verdict

**Livopty n'a pas de design system cohérent. Il a deux systèmes concurrents et des styles dispersés.**

- **Système A, inutilisé** : les tokens shadcn de `global.css` (`--primary`, `--muted`, etc.) et les composants `components/ui/` (`Button`, `Input`, `Text`, `Card`). Ce sont les valeurs par défaut du gabarit : `--primary` vaut `240 5.9% 10%`, c'est-à-dire **presque noir**. La marque n'y apparaît pas.
- **Système B, réellement visible** : du violet et du gris codés en dur dans chaque écran (`bg-purple-600`, `#7c3aed`, `text-gray-500`, `text-zinc-500`, etc.).
- **Typographie en triple** : les tailles `h1`…`h6` dans `tailwind.config.js`, `TEXT_STYLES` dans `lib/constants/fonts.ts`, le composant `StyledText` (utilisé dans un seul fichier) et `components/ui/text.tsx`.

### Design system minimal proposé

Ne pas inventer un nouveau système : **réutiliser les tokens shadcn déjà en place et y mettre la marque.**

**1. Couleurs (`global.css`)**, 10 tokens suffisent :

```css
:root {
  --background: 0 0% 100%;
  --foreground: 240 10% 10%;
  --primary: 262 83% 58%; /* violet de marque, #7c3aed */
  --primary-foreground: 0 0% 100%;
  --muted: 260 20% 97%; /* fonds de champs, cartes */
  --muted-foreground: 240 4% 40%; /* texte secondaire, contraste ≥ 4.5:1 */
  --border: 240 6% 90%;
  --destructive: 0 72% 51%;
  --success: 142 71% 35%;
  --warning: 38 92% 45%;
}
.dark:root {
  /* mêmes noms, valeurs sombres */
}
```

Règle : **aucune couleur nommée (`purple-600`, `gray-500`) ni hexadécimale dans `app/` et `components/custom/`**. Une règle ESLint (`no-restricted-syntax` sur les littéraux `#…`) ou une simple recherche dans la CI suffit à la faire respecter.

**2. Typographie** : une seule source. Garder `components/ui/text.tsx` et lui ajouter une prop `variant` (`title`, `heading`, `body`, `caption`, `label`) qui mappe vers les classes Tailwind. Supprimer `StyledText` et `TEXT_STYLES`. Une seule police : Outfit (retirer Inter).

**3. Espacements et rayons** : échelle Tailwind par 4 (`gap-2`, `gap-4`, `p-4`, `p-6`). Deux rayons seulement : `rounded-2xl` pour les contrôles et cartes, `rounded-full` pour les avatars et pastilles. Aligner `components/ui/button` et `input` sur `rounded-2xl`.

**4. Composants à mutualiser (6)** :

| Composant                         | Remplace                                   | Contenu                                                                                                     |
| --------------------------------- | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `Button` (existant, à rebrancher) | les `TouchableOpacity` violets             | variantes `primary`, `secondary`, `ghost`, `destructive` ; prop `loading` ; hauteur 52 ; libellé accessible |
| `FormField`                       | les 6 blocs copiés de l'auth               | label, `Input`, message d'erreur, icône à droite optionnelle                                                |
| `Screen`                          | `SafeAreaView` + `bg-white` répétés        | fond `bg-background`, safe area, padding standard                                                           |
| `EmptyState`                      | rien (manquant)                            | icône, titre, phrase, bouton d'action                                                                       |
| `ListItem`                        | `LinkedItem`, `ChatItem`, `GroceryFolders` | ligne standard : icône/avatar, titre, sous-titre, chevron                                                   |
| `ToastProvider`                   | `Toast` + `useToast` par écran             | un seul, global                                                                                             |

**5. Icônes** : Lucide uniquement. Supprimer les 30 fichiers de `lib/icons/` et appeler `cssInterop` une fois dans un module `lib/icons.ts`, ou passer `color` explicitement. Remplacer Ionicons par les équivalents Lucide (`ChevronLeft`, `Eye`, `EyeOff`, `AlertCircle`).

### Les 20 % qui donneront 80 % du résultat perçu

1. **Mettre le violet de marque dans `--primary`** et remplacer les violets codés en dur par `bg-primary` / `text-primary` (une passe de recherche-remplacement).
2. **Corriger les onglets** : icônes qui utilisent `color`, fond via token, pas de pastille violette fixe sur Home, libellés traduits.
3. **Un seul bouton principal** (`Button` avec `loading`) partout.
4. **Un `EmptyState`** sur Listes, Discussions, Budget, Agenda : c'est ce qu'un nouvel utilisateur verra en premier dès que les mocks seront retirés.
5. **Forcer le mode clair** (`userInterfaceStyle: "light"`) tant que le mode sombre n'est pas fait, pour supprimer les écrans illisibles.
6. **Remplacer `text-zinc-400` et `text-gray-400`** par `text-muted-foreground` (contraste conforme).
7. **Compresser `assets/images/cover.jpg`** (1,7 Mo) en WebP de 200 à 300 Ko.

## 7. Performance

L'app est petite et la performance n'est **pas** un problème aujourd'hui. Optimisations utiles seulement :

1. **`cover.jpg` de 1,7 Mo** sur le premier écran : le passer en WebP 1080 px (≈ 200 Ko) et utiliser `expo-image`, qui gère le cache et le fondu nativement.
2. **Retirer les dépendances inutilisées et la police Inter** (H4) : démarrage plus rapide, bundle plus léger.
3. **Animations clavier hors thread natif** (M6).
4. **Pas de mémoïsation à ajouter maintenant** : les listes sont courtes. À revoir quand les données viendront de Supabase (pagination, `FlashList` si une liste dépasse quelques centaines d'éléments).
5. Le jour où les données arrivent : un cache de requêtes (**TanStack Query**) évitera les rechargements à chaque changement d'onglet et donnera les états loading, error et refetch gratuitement.

## 8. Architecture cible (simple)

Garder Expo Router et les Contexts. Ajouter seulement ce qui manque pour brancher des données réelles :

```
app/
  (auth)/          welcome, login, register, verify-otp, forgot-password
  (app)/           layout protégé (redirige si pas de session)
    (tabs)/        lists, budget, home
    settings/      index, account, delete-account
  _layout.tsx      providers + garde de route unique
components/
  ui/              Button, Input, Text, Card, FormField, Screen, EmptyState, ListItem
  features/        lists/, budget/, settings/   (composants métier)
lib/
  supabase/        client.ts, database.types.ts (généré par `supabase gen types`)
  api/             lists.ts, budget.ts, couple.ts  (une fonction par requête, comme authService)
  hooks/           useLists(), useBudget()...      (TanStack Query autour de lib/api)
  context/         AuthContext uniquement
  i18n/, schemas/, constants/
supabase/
  migrations/      schéma SQL + RLS versionnés
  functions/       delete-account
```

Règles :

- **L'UI n'importe jamais `supabase` directement** : elle passe par un hook qui passe par `lib/api`.
- **Pas de Redux, Zustand ni de couche "repository"** : TanStack Query pour les données serveur, Context pour l'auth, `useState` pour le reste.
- **Types générés** depuis Supabase, jamais écrits à la main (remplace `lib/types/*` et les types de `lib/data/*`).
- `lib/data/*` (mocks) supprimés au fur et à mesure que chaque écran est branché.

## 12. Produit et business model

**Proposition de valeur** : un espace unique pour organiser la vie à deux (courses, dépenses, planning), là où les couples jonglent aujourd'hui entre WhatsApp, Notes, Splitwise et Google Agenda.

**Cibles** : couples qui vivent ensemble (25 à 40 ans), colocations par extension.

**Ce qui crée de la valeur** : la **synchronisation à deux en temps réel** (listes) et la **clarté financière** ("qui doit combien"). La messagerie n'en crée pas : elle concurrence WhatsApp, et WhatsApp gagne.

| Modèle       | Pertinence        | Détail                                                                                                                                                          |
| ------------ | ----------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Gratuit      | Pour le démarrage | Coût Supabase quasi nul en dessous de quelques milliers d'utilisateurs (offre gratuite, puis environ 25 $/mois)                                                 |
| **Freemium** | **Recommandé**    | Gratuit : listes partagées illimitées, budget simple. Premium : catégories et historique de budget, export, objectifs d'épargne communs, thèmes, pièces jointes |
| Abonnement   | Oui, en premium   | Un seul abonnement **pour le couple** (argument fort) : 2,99 €/mois ou 24,99 €/an                                                                               |
| Achat unique | Secondaire        | Option "à vie" à 49,99 € qui plaît aux réfractaires à l'abonnement ; à tester plus tard                                                                         |
| B2B          | Faible            | Éventuellement des partenariats (enseignes de courses via la recherche produits, banques pour le budget). Pas maintenant                                        |
| Publicité    | Non               | Dégrade une app intime et quotidienne, revenu faible à petite échelle                                                                                           |
